# AC090's integer core and FPU

The 68000-family core OpenQL runs: `ac090.c` (the integer core, with `ac090_mmu.c` and `ac090_fpu.c` included into it) and `ac090.h`. It is AmiCradle's AC090 core, interpreter only: the QL's 68008 model and the Super QL's 68040 model with its FPU. AmiCradle's JIT, magic functions and task cores are not here.

It comes from gfoscpuemulators' `m68k-ac090/native`, as DalsinAI/amicradle holds it at `machines/cpus/` (last taken from amicradle 49447644, 4 Nov 2026, with the interpreter's plain-instruction runs). Its history is there. Take a newer core by copying `ac090.c` and `ac090.h` from there, then run `make test` and the boot checks.

The FPU is OpenQL's own past that point. On x86 hosts FP0-FP7 are the x87's 80-bit long double, as in AmiCradle. Elsewhere (ARM64: Apple silicon, Linux on a Raspberry Pi) `ac090.h` holds them as the 80 bits themselves (`AC090_FPU_SOFT`) and `fpu_soft.c` does the arithmetic in integers: `fpu_special.h` carries AmiCradle's integer extended arithmetic (its Pi 5 work, `fx_arith_fast` and the rest), and `fpu_soft.c` builds every instruction on it to give the x87 build's bits, with the transcendentals in double-double. `fpu_decimal.c` does packed decimal for both, in big integers. `fpu_soft_tables.h` is written by `fpu_soft_gen.py`. So a newer `ac090.h` from AmiCradle needs its `fp` and `fp_tmp` fields kept as `ac090_fpreg`, and `tests/fpu_test.c` (in `make test`) holds both builds to the same results.
